CPU 缓存与数据局部性

缓存层次、缓存行、伪共享、AoS 与 SoA

引言：缓存决定性能上限

同样的算法，只调整内存访问顺序，性能就可能相差一个数量级。差别不在指令条数，而在数据是否命中缓存：一次 L1 命中约 4 个周期，一次主存访问约 200~300 个周期。理解缓存，才是理解“高性能”的起点。

层级典型延迟典型容量谁在管理
L1 Cache4~5 个周期32~64 KB硬件
L2 Cache10~20 个周期256 KB~2 MB硬件
L3 Cache30~70 个周期8~64 MB硬件（多核共享）
主存200~300 个周期GB 级操作系统 + 硬件

表里最重要的不是绝对数字，而是数量级差异：一次缓存未命中的时间，足够执行上百条算术指令。优化的方向因此很明确——让热数据留在 L1/L2，把随机访问改成顺序访问。

一、缓存层次与缓存行

CPU 不以字节为单位搬运数据，而以 64 字节的缓存行（cache line）为单位。哪怕只读一个 int，也会把相邻的 60 个字节一起拉进缓存；反过来，一次未命中也会让整条缓存行失效。这决定了“连续访问”永远比“跳跃访问”便宜。

// 行优先遍历：同一缓存行被连续使用，命中率高
constexpr int N = 1024;
int matrix[N][N];

long long sum_row_major() {
    long long sum = 0;
    for (int i = 0; i < N; ++i)
        for (int j = 0; j < N; ++j)
            sum += matrix[i][j];   // 下一次访问通常仍在同一缓存行
    return sum;
}

long long sum_col_major() {
    long long sum = 0;
    for (int j = 0; j < N; ++j)
        for (int i = 0; i < N; ++i)
            sum += matrix[i][j];   // 每步跨越 4 KB，几乎必然未命中
    return sum;
}
最佳实践：多维数组按行优先存储时，最内层循环必须遍历最后一维；确实需要跨维遍历时，先考虑转置或分块（tiling），让工作集落进 L2。

二、伪共享与数据布局

伪共享（false sharing）发生在两个核心分别写不同变量，而这两个变量恰好落在同一条缓存行：缓存一致性协议以缓存行为单位失效，于是两个核心互相“踢”掉对方的行，性能退化成串行。

#include <atomic>

// 错误写法：两个计数器相邻，极可能共享一条缓存行
struct Counters {
    std::atomic<long long> a{0};
    std::atomic<long long> b{0};
};

// 正确写法：各自按 64 字节对齐，独占缓存行
struct alignas(64) PaddedCounter {
    std::atomic<long long> value{0};
};
static_assert(sizeof(PaddedCounter) == 64, "每个计数器应独占一条缓存行");

图 1：两个核心写同一缓存行的不同变量，缓存行在核心之间来回失效。

陷阱：只给变量加 alignas(64) 还不够——如果结构体被放进数组，相邻元素仍可能共享缓存行；要连同数组步长一起对齐。

三、访问模式与选型

布局选择本质上是空间局部性的取舍：一次只用一个字段，选 SoA；一次要用整个对象，选 AoS。判断依据是访问模式，而不是“哪种写法更现代”。

结论：先用性能剖析确认瓶颈在内存，再改布局；没有测量的“优化”多数只是把代码写复杂。

四、总结与最佳实践

  1. 先测再改：用 perf stat 看 cache-misses，而不是凭直觉重排循环。
  2. 顺序优先：能让最内层循环连续访问，就不要跨步；必要时先转置。
  3. 分块：把工作集切到 L2 能容纳的尺寸，典型块大小为 256~512 个元素。
  4. 隔离热点：高频写的计数器按 64 字节对齐，避免伪共享。
  5. 按访问模式选布局：批量字段计算用 SoA，整体对象传递用 AoS。

缓存优化的本质，不是记住更多技巧，而是养成一种习惯：写每一行访问代码时，都问一句“这条数据现在在哪一层？”。
